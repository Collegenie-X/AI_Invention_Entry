# 미네르바 렌즈로 다시 보는 「바이브코딩 아이디어 50선」

> 목적: 아이디어 목록을 **"만들 것"의 목록**이 아니라 **"검증할 주장"의 목록**으로 바꾸는 것.
> 도구: 미네르바 대학의 HC(Habits of Mind & Foundational Concepts) — 전공과 무관하게 모든 상황에 옮겨 쓰는 사고 도구.

---

## 0. 미네르바의 렌즈란 무엇인가

미네르바에는 "정답 강의"가 없다. 대신 수업마다 **전이 가능한 사고 도구(HC)** 하나를 꺼내 실제 사례에 적용하고, 교수는 답이 아니라 **적용의 정확도**를 채점한다.

이 문서에서 쓸 핵심 HC 8개:

| HC | 한 줄 정의 | 이 프로젝트에서의 질문 |
|---|---|---|
| `#rightproblem` | 지금 푸는 게 진짜 문제인가 | "잔반"이 문제인가, "메뉴 결정권 없음"이 문제인가 |
| `#problemdefinition` | 문제를 측정 가능한 형태로 진술 | "무엇이 몇 %에서 몇 %로 바뀌면 해결인가" |
| `#gapanalysis` | 현재 상태 → 목표 상태의 간극 분해 | 간극이 지식·동기·도구 중 어디에 있나 |
| `#breakitdown` | 큰 문제를 독립 부분으로 절단 | 3개 화면으로 줄일 때 무엇을 버리나 |
| `#constraints` | 자원·시간·권한의 실제 경계 | 주말 2일, 돈 0원, 사용자 = 같은 반 |
| `#optimization` | 제약 아래 목적함수 최대화 | 무엇을 최대화? 점수? 사용자 수? 배움? |
| `#testability` | 반증 가능한 형태로 만들기 | 실패했다는 걸 무엇으로 알 수 있나 |
| `#confounders` | 관찰된 효과의 대안 설명 | 잔반이 준 건 앱 때문인가, 메뉴가 바뀌어서인가 |

**핵심 전환:** 50선 문서는 `#breakitdown`과 `#constraints`는 매우 잘 되어 있다(난이도 ★, 화면 3장, 무료 API). 그러나 `#rightproblem`, `#testability`, `#confounders`가 통째로 비어 있다. 심사 질의응답에서 무너지는 지점이 정확히 여기다.

## 1. 50선 문서 자체를 HC로 진단하기

### 잘 된 것
- `#constraints` — "주말 2일, 무료, 화면 3장". 제약을 먼저 못 박은 건 미네르바식으로 매우 옳다.
- `#utility` — 심사 배점표를 역설계해 "실행 흔적"이 목적함수임을 특정했다.
- `#sourcequality` — 출처를 명시했다. (다만 아래 구멍 참조)

### 구멍 4개

**구멍 1 — 아이디어가 "해결책 목록"이지 "문제 목록"이 아니다** `#rightproblem`
50개 항목 중 대부분이 `문제` 칸에 이미 해결책이 들어가 있다. "급식 잔반 예측기"는 해결책이지 문제가 아니다. 문제는 *"학생이 안 먹을 메뉴가 반복 배식된다"*이고, 예측기는 그중 하나의 가설일 뿐이다. 이렇게 적어두면 예측기가 실패해도 문제는 살아있고, 다른 해결책으로 갈아탈 수 있다.

**구멍 2 — 성공 기준이 없다** `#testability` `#problemdefinition`
"난이도 ★★"는 만드는 비용이지 **성공 조건**이 아니다. 모든 항목에 빠진 한 줄: *"이 앱이 성공했다면 관측될 숫자."*

**구멍 3 — 근거의 표본이 편향돼 있다** `#biasmitigation` `#sourcequality`
"디지털 안전 계열이 수상 확률 가장 높다"는 **수상작만 본 생존자 편향**이다. 분모(그 계열로 출품했으나 떨어진 수)가 없다. 실제로는 "출품 수가 많은 계열"일 가능성이 크고, 그렇다면 경쟁이 가장 치열하다는 정반대 결론이 나온다.

**구멍 4 — 목적함수가 흐리다** `#optimization`
"수상"을 최대화할 것인가, "실제 사용자 문제 해결"을 최대화할 것인가. 두 목적은 대개 같은 방향이지만 갈라지는 순간이 온다(예: 화려한 AI 기능 vs 반 친구가 실제로 매일 쓰는 단순 기능). 지금 정해두지 않으면 마감 직전에 흔들린다.

## 2. 미네르바식 "문제점 찾는 법" 10가지 + 실전 예시

각 방법은 **① 원리 → ② 질문 문장 → ③ 50선 아이디어에 적용한 실제 예시** 순.

### ① 5 Whys 역추적 — 증상과 원인을 분리 `#rightproblem`
> 질문: "왜?"를 5번. 3번째쯤에서 원래 아이디어가 무너지면, 그건 좋은 신호다.

**예시 — #1 급식 잔반 예측기**
잔반이 많다 → 왜? 안 좋아하는 메뉴가 나온다 → 왜? 학생 선호가 반영 안 된다 → 왜? 영양사가 학생 데이터를 못 받는다 → 왜? **의견 수집 통로가 종이 설문 연 1회뿐이다.**
→ **진짜 문제는 예측이 아니라 "피드백 지연"이다.** 만들 것이 바뀐다: 예측 AI(★★★, 데이터 부족)가 아니라 **급식 1분 평점 수집기 + 영양사용 주간 리포트**(★, 데이터 자가생산). 난이도는 내려가고 채택 가능성은 올라간다.

### ② 문제를 숫자 문장으로 강제 변환 `#problemdefinition`
> 질문: "___가 ___에서 ___로 바뀌면 해결이다"를 빈칸 없이 쓸 수 있는가.

**예시 — #23 거북목 감시 웹캠**
나쁜 진술: "학생들이 자세가 나쁘다."
좋은 진술: "우리 반 25명 중 **하루 2시간 이상 고개 각도 30도 초과** 학생이 현재 N명 → 2주 뒤 N/2명."
→ 이 문장을 쓰는 순간 **먼저 측정부터 해야 한다**는 게 드러난다. 측정 도구가 곧 1차 산출물이고, 경고 기능은 2차다. 순서가 뒤집힌다.

### ③ 이해관계자 지도 — 누가 이득이고 누가 손해인가 `#multipleagents`
> 질문: 이 서비스가 완벽히 작동할 때 **불편해지는 사람**은 누구인가.

**예시 — #10 단톡방 괴롭힘 온도계**
이득: 피해 학생, 담임. 손해: **지목당한 학생(오탐 시 낙인)**, 대화를 붙여넣기 당한 제3자(동의 없는 프라이버시 침해).
→ 설계가 바뀐다: 가해자 지목형 → **"이 대화방에서 당신이 소외되고 있는지" 본인 확인용**으로 방향 전환. 심사 질문 *"오탐이면 어떡하죠?"*에 대한 답이 설계 자체에 들어간다.

### ④ 제약 뒤집기 — 자원을 0으로 놓아보기 `#constraints`
> 질문: 인터넷이 없다면? 스마트폰이 없다면? 예산이 0이라면? 그래도 남는 핵심은?

**예시 — #26 위험 등굣길 지도**
서버·계정·앱을 다 뺀다 → 남는 것: **종이 지도 + 스티커**. 이걸로 1주일 돌려보면 제보가 몇 건 들어오는지 알 수 있다.
→ 제보가 3건뿐이면 앱을 만들어도 3건이다. **앱을 만들기 전에 문제의 크기를 아날로그로 측정**하는 것이 미네르바식이다. 그리고 이 종이 실험 사진이 그대로 "실행 흔적" 증거가 된다.

### ⑤ 반증 설계 — 실패 조건을 먼저 쓴다 `#testability`
> 질문: 어떤 결과가 나오면 나는 이 아이디어를 **버릴 것인가**.

**예시 — #29 분식집 웨이팅 예측**
반증 조건: "요일·시간대만으로 예측한 오차가 **그냥 평균값으로 찍은 것보다 나쁘면** 폐기."
→ 이 기준선(baseline) 비교가 있으면 발표가 완전히 달라진다. "AI를 썼습니다"가 아니라 "**단순 평균 대비 오차 34% 감소**"가 된다. 심사위원이 듣고 싶은 건 후자다.

### ⑥ 교란변수 사냥 `#confounders`
> 질문: 내가 본 효과의 **다른 설명**을 3개 대라.

**예시 — #42 공부 집중 타이머**
"앱 쓴 뒤 집중 시간이 늘었다" → 대안 설명: (a) 시험 기간이라 원래 는다 (b) 측정된다는 걸 알아서 늘었다(호손 효과) (c) 앱을 계속 쓴 사람만 남았다(생존 편향).
→ 대응 설계: **같은 사람 안에서 앱 켠 날/끈 날 교차 비교**. 중학생이 이 말을 하면 심사에서 즉시 눈에 띈다.

### ⑦ 분석 수준 이동 `#levelsofanalysis`
> 질문: 개인 / 학급 / 학교 / 제도 중 어느 층위에서 푸는 게 가장 싼가.

**예시 — #48 교복 물려주기 매칭**
개인 층위: 매칭 앱(사용자 100명 필요, 확보 어려움).
학교 층위: **학기말 교복 반납함 1개 + 사이즈 라벨**(운영 주체 = 학생회, 앱 불필요).
→ 앱이 정답이 아닐 수 있다는 걸 스스로 말할 수 있으면, 그때 만든 앱은 훨씬 설득력이 있다. *"층위를 비교한 결과 앱이 필요한 지점은 '사이즈 검색'뿐이었다"* — 이 한 문장이 기획력의 증거다.

### ⑧ 유추(analogy) 이식 — 다른 분야의 해결 구조 빌리기 `#analogies`
> 질문: 구조가 같은 문제를 **이미 해결한 다른 분야**는 어디인가.

**예시 — #6 화장실 혼잡도**
구조적 동일 문제 = 주차장 만차 표시, 카페 웨이팅, 서버 부하 분산.
→ 이들의 공통 해법은 예측이 아니라 **"실시간 표시 + 분산 유도"**. 적용하면 히트맵보다 *"3층은 지금 붐빔 → 4층 권장"* 한 줄이 낫다. 기능이 줄고 효과는 커진다.

### ⑨ 사전 부검(Pre-mortem) `#riskassessment`
> 질문: 6주 뒤 이 프로젝트는 **실패했다**. 부고 기사를 써라.

**예시 — #16 아기 울음 분류기**
부고: *"녹음 데이터를 30개밖에 못 모아 정확도 40%에 그쳤고, 실제 아기에게 접근할 수 없었다."*
→ 사전에 알았으므로 선택지: (a) 공개 데이터셋 확보 여부를 **오늘 확인** (b) 안 되면 주제 교체 (c) '분류'가 아니라 '울음 시각·길이 기록 일지'로 축소.
→ 사전 부검은 착수 전 30분에 하는 것이 규칙이다. 착수 후엔 매몰비용 때문에 못 버린다.

### ⑩ 페르미 추정으로 규모 검산 `#estimation` `#plausibility`
> 질문: 이 문제의 크기를 **자릿수**로 대라.

**예시 — #33 탄소 발자국 급식 계산기**
급식 1인 1식 ≈ 1kg CO₂ 급 → 전교생 500명 × 180일 ≈ 90톤/년.
→ 자릿수가 나오니 목표가 잡힌다: *"메뉴 2개만 저탄소로 바꿔도 연 5톤"*. 반대로 규모가 우습게 작게 나오는 아이디어는 여기서 조기 탈락시킨다. **계산 30분이 6주를 아낀다.**

## 3. 문제를 "제대로 인식"하는 4단계 절차

발견한 문제를 다루는 순서. 각 단계는 산출물이 있어야 넘어간다.

```
1단계  증상 수집   → 관찰 노트 10줄 (내가 본 것만, 해석 금지)
2단계  문제 진술   → "누가 / 언제 / 무엇을 못 해서 / 어떤 손해" 한 문장
3단계  경계 설정   → 이번에 안 다룰 것 3개를 명시 (범위 무한 방지)
4단계  성공 지표   → 숫자 1개 + 측정 방법 + 반증 조건
```

**문제 진술 템플릿 (그대로 채워 쓸 것)**
> **누가**: 우리 반 학생 25명 중 급식 잔반을 자주 남기는 약 10명
> **언제**: 특정 메뉴(생선·나물)가 나오는 주 2회
> **무엇을 못 해서**: 메뉴 선호를 사전에 전달할 통로가 없어서
> **손해**: 1인 1식 약 80g 폐기 + 오후 수업 중 배고픔 호소
> **이번에 안 다룰 것**: 조리법 개선, 예산, 타 학년
> **성공 지표**: 4주 뒤 해당 메뉴 잔반량 20% 감소 (급식실 잔반통 무게 주 2회 측정)
> **반증 조건**: 평점 응답률이 반 인원의 30% 미만이면 통로 가설이 틀린 것 → 폐기

이 한 블록이 있으면 심사 질의응답의 8할이 방어된다.

## 4. 해결책을 "자원에 따라" 찾는 방법

> 사용자의 질문 그대로: 해결책은 자원에 따라 무수히 많다. 그 탐색을 체계화하는 법.

### 4-1. 해결책 사다리 — 같은 문제, 5단계 자원
문제 하나당 **반드시 5칸을 다 채운다.** 위에서부터 채우면 아래 칸이 안 나오므로, **0원 칸부터** 쓴다.

| 자원 수준 | 형태 | 급식 잔반 예시 | 등굣길 위험 예시 |
|---|---|---|---|
| **L0 · 0원, 0코드** | 종이·말·규칙 | 급식실 앞 스티커 투표판 | 종이 지도 + 위험지점 스티커 |
| **L1 · 기존 도구 조립** | 구글폼/스프레드시트 | 구글폼 QR + 자동 그래프 | 카카오맵 즐겨찾기 공유 |
| **L2 · 단일 HTML 앱** | localStorage, 서버 없음 | 1분 평점 웹앱 + 주간 리포트 | Leaflet 제보 지도(로컬 저장) |
| **L3 · 데이터 결합** | 공공API + 축적 데이터 | 나이스 급식 API × 평점 이력 | 지도 × 가로등 공공데이터 |
| **L4 · 학습 모델** | Teachable Machine 등 | 메뉴 특성→잔반 회귀 예측 | 제보 사진 위험유형 자동분류 |

**규칙 3개**
1. **L0을 1주 돌려보지 않고 L2 이상으로 가지 않는다.** L0에서 사용자가 안 쓰면 L4에서도 안 쓴다.
2. **각 단계는 이전 단계의 데이터를 물려받는다.** L0 스티커 투표 = L4 모델의 학습 데이터. 버리는 단계가 없어야 6주가 축적된다.
3. **제출은 L2~L3에서 한다.** L4는 "다음 단계" 슬라이드로 남긴다. 완성 못 한 L4보다 작동하는 L2가 항상 이긴다.

### 4-2. 발산 → 수렴 프로토콜

**발산 (30분, 판단 금지)**
- **자원 축**: 사다리 5칸 × 아이디어 2개 = 10개
- **주체 축**: 학생이 푼다 / 교사가 푼다 / 시스템이 자동으로 / 아무도 안 풀어도 되게 문제를 없앤다
- **시간 축**: 사전 예방 / 실시간 개입 / 사후 기록
- **유추 축**: 다른 분야의 같은 구조 해법 3개 (⑧번 방법)

→ 보통 20~30개가 나온다. 여기서 처음 떠오른 것(대개 "AI로 ○○ 판별")은 **거의 항상 상위 5위 안에 못 든다.**

**수렴 (점수표, 1~5점)**

| 기준 | 가중치 | 질문 |
|---|---|---|
| 문제 적중도 | ×3 | 5 Whys의 **뿌리**를 건드리는가, 증상만 건드리는가 |
| 검증 속도 | ×3 | **7일 안에** 맞았는지 틀렸는지 알 수 있는가 |
| 자원 적합 | ×2 | 내가 이미 가진 것(반 친구·무료API·주말)만으로 되는가 |
| 데이터 축적 | ×2 | 다음 단계로 데이터가 이어지는가 |
| 실패 회수 | ×1 | 실패해도 남는 것(측정 도구·데이터·기록)이 있는가 |

합계 최고점 **1개만** 실행한다. 2위는 "L0으로만" 병행 가능.

### 4-3. 되돌릴 수 있는 결정과 없는 결정 `#decisiontree`
- **되돌릴 수 있음**(기술 선택, UI, 기능 추가/삭제) → **고민 말고 즉시 실행.** 30분 이상 고민하는 건 낭비.
- **되돌리기 어려움**(주제 선정, 사용자 집단, 데이터 수집 방식) → **사전 부검 + 페르미 검산을 반드시 통과시킨 뒤** 결정.
> 중학생 프로젝트에서 되돌릴 수 없는 결정은 사실상 **"무슨 문제를 고를 것인가"** 하나뿐이다. 그러니 시간의 대부분을 여기에 쓰고, 나머지는 빠르게 만들며 배운다.

### 4-4. 반복 루프 (2주 단위)
```
문제 진술 → L0 실험 → 관측 숫자 → 진술 수정 → L2 구현 → 사용자 5명 → 반증 확인
                ↑                                                      │
                └──────────  틀렸으면 진술로 되돌아간다  ───────────────┘
```
**되돌아간 횟수 자체가 포트폴리오다.** 디미고 동점자 1순위 항목인 "실행 흔적", 코드페어의 "연구 데이터"가 정확히 이 루프의 기록이다. 한 번에 성공한 프로젝트보다 **"3번 틀리고 4번째에 맞춘 기록"**이 훨씬 강하다.

## 5. 오늘 당장 할 수 있는 것

1. 50선에서 **끌리는 3개**를 고른다.
2. 각각에 **5 Whys**(방법 ①)를 적용한다 — 30분. 대개 1~2개는 여기서 무너진다.
3. 살아남은 것에 **§3 문제 진술 템플릿**을 채운다 — 30분.
4. **해결책 사다리 L0 칸**을 쓰고, **이번 주에** 그걸 실행한다 — 종이·구글폼이면 충분.
5. L0 결과 숫자를 들고 다시 판단한다. 그때 코드를 짜기 시작한다.

> 미네르바식 한 줄 요약:
> **"무엇을 만들까"를 묻지 말고, "내가 틀렸다는 걸 가장 싸게 알아내는 방법은 무엇인가"를 물어라.**
