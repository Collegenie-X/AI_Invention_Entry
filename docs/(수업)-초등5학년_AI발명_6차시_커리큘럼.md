# 0. 한눈에 보는 6차시 요약

> 이 장만 읽어도 6차시 전체가 파악되도록 정리했습니다. 상세 지도안은 3장부터입니다.

## 0.1 6차시 한 줄 요약

| 차시 | 제목 | **무엇을 배우는가 (핵심 개념)** | 무엇을 하는가 (활동) | 산출물 |
|---|---|---|---|---|
| **1** | 완성품을 만나고 문제를 찾는다 | **특징으로 구분한다** — 사람도 AI도 '특징'을 보고 판단한다 / 예측을 먼저 적는 습관(P·R) | 완성 예제 예측→실행 · 불편함 20개 사냥 | 예측 기록지 · 팀 주제 1개 |
| **2** | 컴퓨터 비전을 뜯어본다 | **입력→특징→분류→신뢰도** / AI는 보기 중에서 고를 뿐 '모름'을 못 말한다 / **조건은 위에서부터 하나만 실행된다** | 실험 A(값)·B(신뢰도)·C(순서) | 조사 기록지 · 클래스 확정 |
| **3** | 피지컬 컴퓨팅을 뜯어본다 | **입력(센서)→판단→출력(액추에이터)** / 프로그램은 한 번에 하나씩 / **켜고→보여주고→지운다** 순서 | 실험 D(값)·E(순서)·F(블록 빼기) | 동작 설계표 · 순서도 |
| **4** | 우리 것으로 고친다 | **학습 데이터의 다양성이 성능을 만든다** / 예제 수정으로 내 것 만들기(Modify) / **한 번에 하나씩 붙이고 확인한다** | 데이터 촬영·학습 · 예제 코드 수정 | 학습된 모델 · 코드 v0.1 |
| **5** | 붙이고 테스트한다 | **테스트는 계획적으로 한다** / 성공이 아니라 **실패를 찾는 것**이 성과 | 마이크로비트 연결 · 하우징 · 테스트 12개 | 시제품 · 실패 기록 10건+ |
| **6** | 고친다 | **원인은 데이터·코드·하드웨어 셋으로 나뉜다** / 한 번에 하나만 고치고 다시 테스트 / 신뢰도 임계값의 트레이드오프 | 개선 2~3회전 · 재테스트 | 개선된 발명품 · 개선 이력표 |

## 0.2 차시별 학습 내용 상세

### 1차시 · 발견 — "구분한다는 것"
- **개념** 특징(feature)의 뜻 / 예측→실행의 학습 순서
- **기능** 완성 예제를 실행하고 관찰 결과를 기록한다
- **태도** 예측이 틀리는 것이 배움의 시작이다
- **판별 질문** "이건 무엇과 무엇을 구분하면 해결되나요?"

### 2차시 · 정의 — "AI는 어떻게 보는가"
- **개념** 입력·특징 추출·분류·신뢰도 4단계 / 조건문의 배타적 실행
- **기능** 값을 바꿔 실험하고, 신뢰도를 읽고, 조건 순서를 재배치한다
- **원리 3가지**
  1. 기다리는 시간이 없으면 결과가 요동친다 (실험 A)
  2. AI는 100%가 아니라 '몇 %'로 말하고, 모르는 것도 억지로 고른다 (실험 B)
  3. 좁고 특별한 조건이 위, 넓고 일반적인 조건이 아래 (실험 C)
- **적용** 클래스 3~4개 + '모르겠음' 확정

### 3차시 · 설계 — "AI의 판단을 몸으로 옮긴다"
- **개념** 센서→판단→액추에이터 / 순차 실행 / 상태를 지우는 타이밍
- **기능** 마이크로비트 LED·소리·센서 블록을 조작한다
- **원리 3가지**
  1. 프로그램은 한 번에 한 가지만 한다 (실험 D)
  2. 지우기를 위에 두면 켜지자마자 사라진다 → 켜고→대기→지우기 (실험 E)
  3. 쉬는 블록을 빼면 오히려 느려진다 (실험 F)
- **적용** 동작 설계표 + 순서도 작성

### 4차시 · 제작 1 — "예제를 우리 것으로"
- **개념** 학습 데이터의 양보다 **다양성**(각도·거리·밝기·장소)
- **기능** 클래스별 촬영·학습, 조건 갈래 추가, 문구·값 수정
- **원리** 두 가지를 한꺼번에 붙이면 원인을 못 찾는다 → 화면 출력부터 검증
- **적용** 우리 코드 v0.1 완성 · 개선 전 영상 기록

### 5차시 · 제작 2 + 테스트 — "언제 안 되는지 찾는다"
- **개념** 조건을 바꿔가며 테스트하는 설계(장소·배경·거리·가림·시간)
- **기능** 하드웨어 연결, 갈래별 순차 검증, 하우징 제작
- **원리** 학습한 환경에서 벗어나면 성능이 떨어진다
- **적용** 테스트 12개 수행 · ✕ 목록 확보

### 6차시 · 개선 — "고쳐지는 것이 발명이다"
- **개념** 원인의 3분류(데이터/코드/하드웨어) / 통제된 개선(한 번에 하나)
- **기능** 재촬영·재학습, 조건 순서·대기시간·신뢰도 임계값 조정, 구조 수정
- **원리** 임계값을 올리면 놓치고, 내리면 틀린다 — 정답은 팀이 정한다
- **적용** 개선 2~3회전 · 이력표로 전후 비교

# 1. 이 수업의 설계

## 1.1 목적 — 프로젝트 한 바퀴를 온전히 돌아본다

이 수업의 목표는 멋진 발명품이 아닙니다. **문제를 찾아 만들고 테스트하고 고치는 한 바퀴**를 학생이 몸으로 겪게 하는 것입니다. 그래서 마지막 차시가 발표가 아니라 **개선**입니다.

```
  ① 발견 ──▶ ② 정의 ──▶ ③ 설계 ──▶ ④ 제작 ──▶ ⑤ 테스트
                                                  │    ▲
                                                  ▼    │
                                                ⑥ 개선 ─┘
                                             (2~3회전 반복)

  무엇이       무엇과 무엇을    어떻게 보고,     만든다      진짜 되나?
  불편한가      구분하면 되나    판단하고,                  언제 틀리나?
                            반응할 것인가
```

대부분의 수업은 ④ 제작에서 끝납니다. 이 수업은 **⑤와 ⑥ 사이를 반복하는 구간에 6차시 중 2.5차시를 씁니다.** 발명은 완성되는 것이 아니라 고쳐지는 것이라는 감각이 여기서 생깁니다.

## 1.2 방법 — PRIMM

백지에서 코딩을 시작하면 초등 5학년은 대부분 막힙니다. 그래서 **이미 작동하는 코드**에서 출발합니다.

```
 ┌───┬──────────────┬────────────────────────────────────────┐
 │ P │ Predict      │ 실행하기 전에 예측한다                     │
 │   │ 예측한다      │ "이 코드를 돌리면 어떻게 될 것 같아?"        │
 ├───┼──────────────┼────────────────────────────────────────┤
 │ R │ Run          │ 돌려보고 예측과 맞춰본다                    │
 │   │ 실행한다      │ "예상대로였어? 뭐가 달랐어?"                │
 ├───┼──────────────┼────────────────────────────────────────┤
 │ I │ Investigate  │ 값을 바꾸고 순서를 바꿔 원리를 찾는다         │
 │   │ 파헤친다      │ "이 숫자를 3으로 바꾸면? 이 줄을 위로 올리면?"│
 ├───┼──────────────┼────────────────────────────────────────┤
 │ M │ Modify       │ 우리 목적에 맞게 고친다                     │
 │   │ 고친다        │ "우리 발명품이 되려면 뭘 바꿔야 하지?"        │
 ├───┼──────────────┼────────────────────────────────────────┤
 │ M │ Make         │ 스스로 이어 만든다                         │
 │   │ 만든다        │ "이제 우리 것을 완성하자"                   │
 └───┴──────────────┴────────────────────────────────────────┘
```

**핵심 규칙 — 예측을 반드시 글로 먼저 적게 합니다.** 예측 없이 실행 버튼부터 누르면 그냥 구경이 되고, 아무것도 남지 않습니다. 예측이 틀렸을 때 배움이 일어납니다.

> **교사 유의** — 예측이 틀린 학생에게 "아니야"라고 하지 마세요. **"오, 그렇게 생각했구나. 왜 그렇게 생각했어?"** 로 받으면 그 다음 실행을 훨씬 집중해서 봅니다.

## 1.5 3인 1팀 역할

역할은 차시마다 한 칸씩 돌립니다. 한 명이 코딩만 하다 끝나는 것을 막기 위해서입니다.

| 역할 | 하는 일 |
|---|---|
| **눈 담당** | 촬영 계획, 사진 수집·정리, 모델 학습 실행 |
| **머리 담당** | 예측 기록, 블록 조립, 값·순서 변경 실험 |
| **몸 담당** | 마이크로비트 연결, 하우징 제작, 테스트 기록 |

| | 1차시 | 2차시 | 3차시 | 4차시 | 5차시 | 6차시 |
|---|---|---|---|---|---|---|
| **A** | 눈 | 머리 | 몸 | 눈 | 머리 | 몸 |
| **B** | 머리 | 몸 | 눈 | 머리 | 몸 | 눈 |
| **C** | 몸 | 눈 | 머리 | 몸 | 눈 | 머리 |

**PRIMM의 예측(P)만은 예외입니다.** 항상 **세 명이 각자 따로** 적은 뒤 비교합니다. 답을 맞히는 게 목적이 아니라 서로 다르게 생각했다는 걸 확인하는 게 목적입니다.

# 2. 학습목표

1. 컴퓨터 비전이 **입력 → 특징 → 분류 → 신뢰도**의 흐름으로 작동함을 예제를 조작해 설명할 수 있다.
2. 피지컬 컴퓨팅이 **입력(센서) → 판단 → 출력(액추에이터)** 구조임을 예제를 조작해 설명할 수 있다.
3. 블록 코드의 **값을 바꾸거나 순서를 바꾸면 동작이 어떻게 달라지는지** 예측하고 확인할 수 있다.
4. 주어진 예제 코드를 **우리 문제에 맞게 수정**해 발명품을 완성할 수 있다.
5. 발명품을 계획적으로 테스트해 **실패 사례를 수집**하고, 원인을 데이터·코드·하드웨어로 나눌 수 있다.
6. 개선 전후를 비교해 **무엇을 고쳐서 무엇이 좋아졌는지** 설명할 수 있다.

# 4. 평가

## 4.1 원칙

**작동 여부로 평가하지 않습니다.** 최종 성능이 좋은 팀이 아니라, **테스트를 성실히 하고 원인을 제대로 나눈 팀**이 잘한 것입니다.

## 4.2 루브릭

| 영역 | 잘함 | 보통 | 노력 요함 |
|---|---|---|---|
| **예측 (P)** | 근거를 들어 예측하고, 틀린 이유를 설명함 | 예측은 적었으나 근거 없음 | 실행부터 함 |
| **조사 (I)** | 값·순서 변경 결과에서 원리를 스스로 말함 | 시키는 대로 바꿔봄 | 조작만 하고 관찰 없음 |
| **수정 (M)** | 예제를 우리 설계에 맞게 정확히 고침 | 일부만 고침 | 예제 그대로 씀 |
| **테스트** | 계획표대로 끝까지 돌리고 실패를 정직하게 기록 | 대충 돌려봄 | 잘 되는 것만 확인 |
| **원인 분석** | 데이터·코드·하드웨어로 정확히 나눔 | 나누기는 함 | "그냥 안 돼요" |
| **개선** | 한 번에 하나씩 고치고 효과를 확인함 | 고쳤으나 확인 안 함 | 고치지 못함 |
| **협업** | 역할을 바꿔가며 참여하고 의견 차를 대화로 해결 | 맡은 역할은 수행 | 특정 활동에만 참여 |

## 4.3 개인 평가의 근거

3인 1팀이라 팀 산출물만으로는 개인을 볼 수 없습니다. 다음 셋이 개인 기록입니다.

1. **예측 기록지** — 매 차시 개인별 작성. PRIMM의 P는 항상 따로 씁니다.
2. **역할 수행** — 로테이션 표에서 자기 담당 차시에 무엇을 결정했는지.
3. **개선 이력표 서명** — 각 회전마다 주도한 학생 이름을 적게 합니다.

# 7. 교사용 메모

## 7.1 PRIMM을 망치는 세 가지

1. **예측을 건너뛰기** — 가장 흔한 실패입니다. 아이들은 실행 버튼을 먼저 누르고 싶어 합니다. 예측지를 걷은 뒤에 실행을 허락하는 방식으로 물리적으로 막으세요.
2. **교사가 답을 먼저 말하기** — "이렇게 하면 이렇게 돼"라고 말하는 순간 조사(I)가 사라집니다. 끝까지 질문으로만 대응하세요.
3. **너무 큰 예제를 주기** — 예제는 **10줄을 넘기지 않아야** 합니다. 크면 뭘 봐야 할지 모릅니다.

## 7.2 시간이 부족할 때

줄이는 순서입니다.

1. 먼저 — 5차시 하우징 제작 (종이컵·상자로 간소화)
2. 다음 — 1차시 불편함 20개를 10개로
3. 다음 — 3차시 실험 F (센서)
4. **절대 줄이지 말 것** — **2차시 실험 C (조건 순서)**, **5차시 테스트 12개**, **6차시 전체**

이 셋이 빠지면 남는 것은 평범한 따라 하기 수업입니다.

## 7.3 3명이라 생기는 일

- **한 명이 다 해버림** — 역할표를 벽에 붙이고, 담당 아닌 학생이 마우스를 잡으면 교사가 개입합니다.
- **의견이 2:1로 갈림** — 다수결로 넘기지 말고 소수 의견을 설계표 여백에 적어둡니다. 6차시 "다음에 해본다면"에 그 의견이 들어가는 경우가 많습니다.
- **한 명 결석** — 타격이 큽니다. 차시 산출물을 반드시 사진으로 남겨 공유하세요.

|---|---|---|
| 웹캠이 안 잡힘 | 브라우저 권한 미허용 | 주소창 카메라 아이콘에서 허용 |
| 마이크로비트 연결 안 됨 | 충전 전용 USB 케이블 | 데이터 전송용으로 교체 |
| 한쪽 클래스로만 분류됨 | 클래스별 사진 수 불균형 | 적은 쪽 보충 후 재학습 |
| 프로그램이 버벅임 | 웹캠 + 시리얼 동시 부하 | 다른 프로그램 종료, 대기 시간 추가 |
| LED가 계속 깜빡임 | 반복문마다 재출력 | 켜기 → 대기 → 지우기 순서 확인 (실험 E) |
| 반응이 한 박자 늦음 | 대기 시간이 김 | 실험 A 결과를 근거로 조정 |
